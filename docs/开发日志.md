## 2026-07-26（日）· Flow 期权流分栏（第 7 个分栏）

四轮 codex review，**共 26 个真缺陷**（5+9+8+3+1）。这是目前最难的一栏 ——
难点不在算法，在**分清"算不出"与"是零"**。

### ⭐ 这一栏的立身之本：先说做不了什么

UW 的 flow 建立在**逐笔成交带（options tape）**上：每笔成交带 size、成交价、
交易所、时间戳。有了它才能判断"打在 ask 还是 bid"，也才有招牌的
**bullish / bearish flow** 标签。

**我们没有 tape，也不会去要** —— 要 tape 就要 OPRA feed，
就要按 redistributor 交 $1,500/月，整个自部署模式当场垮掉。

| 能算（链快照就够） | 算不出（必须有逐笔） |
|---|---|
| vol/OI、P/C 三口径、绝对 delta 敞口、到期与行权分布 | Sweep（毫秒内跨所拆单） |
| **OI 日变化**（本地逐日沉淀，tape 反而给不了） | 大单分级（5,000 手是一笔还是 5,000 笔，快照里一样） |
| | 主动买/主动卖、开仓/平仓 |

⛔ **所以本栏不产出任何方向性标签。** 没有 aggressor side 却写"看涨流入"，
是把猜测当事实卖。这条被写进 `LIMITS` 常量，从 API 到 UI 到 MCP 三处同文出现。

### ⭐ 反过来，快照有 tape 没有的一样东西：持仓量

tape 说**成交了什么**，OI 说**沉淀下来多少**。逐日记 OI，差值就是净新增头寸 ——
"谁在建仓"最硬的证据，而且**不需要猜方向**。代价：每天只更新一次，且**补不回来**，
只能从装上那天起自己攒（这正是 UW 拿来单独卖钱的东西）。

### 归档键：交易时段，不是墙上日期

CBOE 给了三个时间，含义完全不同：

| 字段 | 值（实测） | 是什么 |
|---|---|---|
| `last_trade_time` | `2026-07-24T16:00:00` | **数据所属交易时段**（周五收盘）|
| `timestamp` | `2026-07-25 03:44:48` | CBOE **发布**这份文件的时刻 |
| 墙上时间 | 2026-07-26（周日）| 我打开页面的时间 |

按墙上时间归档，周六周日各打开一次 → 同一份周五数据存成"两天的观测" →
OI 差值全是 0 → 看着像"持仓没变"，其实**根本没有新数据**。
改用 `last_trade_time` 后，重复点击归档不再伪造出第二天（实测天数仍为 1）。

⚠️ 与 GEX 历史的取舍**刻意不同**：GEX 要日内序列，所以按 `timestamp`（发布时刻）
存是对的；OI 是日度结算量，必须按 session 存。**同一个"用数据自己的时间"原则，
落到两个模块是两个不同的字段。**

### Codex 四轮 26 个缺陷 —— 按性质归纳

**A. "算不出"被写成了一个具体的数（9 个，最要命的一类）**

| 场景 | 错误呈现 | 真相 |
|---|---|---|
| 某边全缺 delta | 敞口 `0` | 算不出 |
| 某边全缺报价 | 权利金 `0`、P/C `0.00` | 算不出 |
| 整个到期桶无报价 | `notional: 0` | 算不出 |
| 库里没存过那一天 | 全量清仓 / 全量建仓 | 没存过 |
| 未到期合约在快照里缺席 | 净平仓全部头寸 | **那次抓取不完整** |
| 期间到期的合约消失 | 一大笔净减持 | 只是到期了 |
| 接口 500 | "还没攒够历史" | 服务故障 |
| 清单请求失败 | "无匹配合约 0/0" | 连不上 |
| 利差某腿缺期限 | "三条口径均为正" | 那条算不出 |

**B. 同一份数据两个视图口径不一致（6 个）**

- 持仓量 P/C 算在"今日有成交子集"上却标称"沉淀下来的仓位结构"
  （实测 SPY：2.836 → 修正后 2.517，**差异是真的**）
- 两张分布图一张全行权价、一张 ±15%，合计对不上却不说
- MCP 默认全链、网页默认 7 天，且 MCP 不报自己用的口径
- MCP 不报 `incomplete_excluded`，UI 却打红色警告
- MCP `notional or 0` 把 null 说成 $0
- 归档存的是"有成交子集"，而口径写的是"全链"

**C. 过度断言（3 个）**

- `is_new_strike`（"全新行权价"）→ 改名 `zero_prior_oi`。
  OI=0 只能推出"昨收无未平仓头寸"，推不出"今天全是新开仓" ——
  也可能是**冷门行权价**，或**开了又平的日内往返**（明天 OI 还是 0）。
- "vol/OI>1 通常意味着有新头寸在建" → 改为纯字面表述，
  并明说这份数据**分不出**新建与换手。
- "名义权利金" → 全线改称**估算**：链快照没有成交价，
  算的是「累计成交量 × **抓取时**中间价」。1,000 张上午 $1 成交、
  抓取时中间价 $5 → 显示 $50 万而实际约 $10 万，**差五倍**。

**D. 竞态与并发（3 个）** · **E. 排序误导（1 个）** · **F. 环境假设（2 个）**

- 归档是长请求，返回时闭包里的 `load()` 绑的还是旧标的 →
  输入框写着 QQQ、卡片显示 SPY
- 两天数据分两次查，中间可能夹进一次归档 → 改成一条 `IN (?,?)` 原子读
- 同时段重录用 `INSERT OR REPLACE` 只覆盖传入行 → 改事务内整段替换
- 异动榜把"前收 0"当排序键 → 榜首是三张各值几千美元的深度虚值彩票，
  而当天真正的大动作（739P 成交 86,279 张、$24M）被压到第 5
- **`FULL OUTER JOIN` 要 SQLite 3.39+**，本机 3.53 能跑、
  用户的 macOS 系统 Python 还带着 3.3x → 改成 Python 侧合并
- **项目从未声明最低 Python 版本** → 加 `backend/pyversion.py` 启动闸（3.9）

### ⭐ 三条教训

1. **"取不到 ≠ 没有"这条铁律，栽的从来不是 403。**
   前几栏我一直在防限流被当成没数据。这一栏的 9 次全是别的形状：
   累加器从 0 起步、缺失值只是跳过、`or 0`、`if v` 把 `None` 和 `False` 合并、
   空 `catch`。**"零"是个太顺手的默认值。**

2. **`is_new_strike` 这种名字本身就是断言。**
   变量名把"OI=0"翻译成"全新行权价"，读代码的人（和写代码的我）
   就再也不会去想第三种可能。改叫 `zero_prior_oi` 之后，
   那三种情况自然就浮出来了。

3. **四轮才收敛，且每轮都有"修复引入的新问题"。**
   第二轮 9 个里有 4 个、第三轮 8 个里有 2 个是前一轮修复带进来的。
   ⛔ **复审不是走过场** —— 这条已经在 Market 那栏写过一次，这次更明显。

## 2026-07-26（日）· Market 宏观分栏（第 6 个分栏）

两轮 codex review，共抓出 **9 个真缺陷**（第一轮 5 个、复审又 4 个）。

### 全项目最干净的一条线

Treasury + CFTC 都是 **S 级**：美国政府作品、公有领域，不限商用、可自由再分发。
没有 OPRA、没有 §13107（国会那条禁商用）、没有 FINRA 条款——
这是六个分栏里**唯一一条毫无许可约束**的数据线。

### 数据源实况（2026-07-26 实测）

| 源 | 端点 | 实况 |
|---|---|---|
| Treasury 收益率曲线 | `home.treasury.gov/.../pages/xml?data=daily_treasury_yield_curve&field_tdr_date_value=YYYY` | 按年一份 XML，**单次 8.2 秒 / 278KB**；13 个期限 `d:BC_*` |
| CFTC TFF 持仓 | `publicreporting.cftc.gov/resource/gpe5-46if.json`（Socrata） | 82 字段；收录 **186 个合约、仅 90 个仍在更新**（有的停在 2022 年） |

### ⭐ 四个只有实跑才知道的坑

**① `S&P 500` 里的 `&` 会把 SoQL 查询打成 400。**
手工拼 `f"...like upper('%25{name}%25')"` 进 URL，`&` 被当成参数分隔符。
必须交给 `requests` 的 `params=` 自己编码。

**② 关键词模糊匹配会把不同合约揉成一条锯齿线。**
`like '%S&P 500%'` 同时命中 9 个合约。按日期倒序取 N 行时，
**同一天里哪个合约排前面是任意的** —— 问 `E-MINI S&P 500` 拿到的是 `MICRO E-MINI` 的数字。
而且 `limit` 是**总行数**，多合约命中时 N 行散在几个合约上，根本凑不出时间序列。
→ 改成**先定合约再取序列**：先 group-by 拿全量合约名，精确匹配 → 唯一匹配 → 都不是则
**返回候选清单让调用方自己挑，不替他选**。

**③ 数据集里躺着大量停更合约。**
只给一串名字，用户选中停更的会看到空白——而真相是"这个合约不报了"，
和"取数失败"是两件事。→ 清单必须带 `last_date`，默认只给仍在更新的 90 个。

**④ 收益率曲线该落库，别的源不用。**
取 3 年 = 29 秒。而这份数据有别的源没有的性质：**往年的值永远不会再变**。
→ SQLite 缓存，**按年判新鲜度**：往年够完整就永不再拉，今年按 `MAX(date)` 落后 4 天才重拉
（4 天是为了容下周末+假日）。实测 **26.7s → 0.0s**，扩年份时只补缺的那几年。
⚠️ 缓存的是**数据本身**不是"这年我拉过了"——Treasury 会修订历史值，只记后者就永远发现不了。

## 2026-07-26（日）· Shorts 做空分栏（第 5 个分栏）

六轮 codex review 收敛到 "No discrete, actionable correctness defects"。

### ⭐ 先兑现承诺：动手前查条款

上一轮结尾说过「FINRA 是 B 级源、做之前先把条款查清楚，这个项目已经在合规上错过一次」。
**这次先查、后写代码。** 结果：

FINRA Terms of Use（2023-11-09 版，实读原文）：

| | 原文 |
|---|---|
| Permitted Uses | "shall be used **ONLY for your own non-commercial personal or professional use**" |
| Restrictions (d) | "**develop or create a database of data** using the FINRA Website" |
| Restrictions (e) | "monitor or copy the FINRA Website **in bulk**, or use any **data mining, scraping or harvesting tools**" |

⚠️ **(d) 直接冲击本项目的架构** —— 每个分栏都是「下载 → 落本地 SQLite」。

而且存在**真实的模糊地带**，不该往自己有利的方向解释：
- 条款范围写的是 "the use of the FINRA.**ORG** site"，而 Reg SHO 文件在 `cdn.finra.org`（不同主机名）
- FINRA 另有一套 **API Terms of Service**（点击同意式），需每个用户自己注册接受，我们无法代为接受

**→ 处理方式：FINRA 默认关闭（`VF_ENABLE_FINRA=1` 才启用），UI 上把条款原文与模糊之处
原样摆出来，判断交给用户。主源改用 SEC FTD（S 级、不限商用），不开 FINRA 也完全可用。**

顺带查清：SEC **Form SHO**（Rule 13f-2，机构空头持仓 —— 正是 13F 缺的那块）
2025-02 被豁免延期到 **2026-02-17** 首次申报，聚合数据**至今未公布**。

### ⭐ 三条官方原文（这个分栏的数据全项目最容易读反）

**① FTD 不是当日新增，是累计余额**（SEC 原文）：
> "Fails to deliver on a given day are a **cumulative number of all fails outstanding
> until that day**... **The figure is not a daily amount of fails**... may have little or
> no relationship to yesterday's aggregate fails. Thus... **the age of fails cannot be
> determined** by looking at these numbers."

→ 所以本页**不做日环比、不谈「激增」**，按结算日**刻意用柱不用折线**——
折线会暗示一种并不存在的连续演进。

**② FTD 不是裸卖空的证据**（SEC 原文）：
> "fails-to-deliver can occur for a number of reasons on **both long and short sales**.
> Therefore, fails-to-deliver are **not necessarily the result of short selling, and are
> not evidence of abusive short selling or 'naked' short selling**."

→ 这恰恰是该数据最流行的用法。实测余额最大的是 **XOM / PG / GOOG** 这类
高流动性大盘股，不是小盘股 —— 与「裸卖空打压」的叙事并不吻合。

**③ 空头成交量 ≠ 空头持仓**（FINRA 原文）：
> "short interest position data **does not—and is not intended to—equate to** the daily
> short sale volume data."

且该文件只含**场外**成交（"not consolidated with exchange data"）→
拿它算「全市场做空占比」是错的。

### ⭐ 第三次「审计判错、但根因是真的」

Codex 报「13F 组合报告被丢掉了」。**实测核实：441 份组合报告的 `SUBMISSIONTYPE`
全是 `13F-HR`(410) / `13F-HR/A`(31)，我的过滤器本来就包含它们，一条没丢。**

### ⚠️ 关键设计决定（别改坏）

1. **Gamma Flip 必须用 BS 重算 gamma**，不能复用 CBOE 给的 gamma。
   CBOE 的 gamma 是**当前股价下**的值；flip 要问"如果股价变成 X"，而 gamma 随股价剧烈变化（ATM 最高、两端趋零）。
   第一版用"累计 net_gex 找符号翻转"的简化法，结果返回 `None`（因为全程负）——**那是错的近似**，已弃用。

2. **做市商持仓方向是假设，不是事实。**

3. **找不到 flip 就返回 None**，不硬凑数字。很多标的在合理区间内确实不翻转。

| 13 | 零敞口报成 negative；改完又漏改 MCP summary | 边界值要有 neutral；**加了状态就要全链路跟上** |

### ⭐ 三条可复用的教训

1. **「同一份数据的两个视图，必须走同一套过滤条件」** —— 13 个问题里有 4 个是这类（1/4/8/12）。
2. **异常分类必须正向识别** —— 403 当成「没数据」，会让"被封 IP"永远查不出来。这条与 global-stock-data v2.0.1 的根因完全一致，**同一个错我犯了两次**。
3. **测试要覆盖参数空间的边界**，不只是主力标的 —— 低价股那个 bug 只有测 $14 的票才暴露。
